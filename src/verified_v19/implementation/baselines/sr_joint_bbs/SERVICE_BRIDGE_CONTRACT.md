# SR verifier and Agent bridge contract

The trusted configuration is selected by `config_id`; request JSON cannot supply or override it. It fixes the deployment identifier, full Joint circuit-id field, legacy `(system=0,circuit_version=1)` mapping, exact BBS verifier material and parameter digest, issuer key, and a one-to-one map from `(tuple_version, snapshot_digest)` to the complete atomic snapshot. A verifier rejects an unknown deployment, another full circuit id, another parameter digest, a reused tuple version with a different snapshot, or a showing whose disclosed legacy fields differ from this mapping.

`sr-verify` input contains `config_id`, the canonical base-request bytes, complete atomic snapshot and digest, terminal, resource, one-hot action, request interval, nonce, and base64 canonical showing. The adapter constructs `RequestContext` itself and returns only `{valid:true}` after BBS verification. The HTTP service then performs the same trusted-clock retirement check, terminal signature verification, and atomic nonce/resource commit used for Joint. Delta zero accepts only the current mapped snapshot. A positive Delta uses the service's authenticated `retired_at` history and repeats the check inside the commit transaction.

The Agent side receives an issued credential and prover material through a trusted local channel, constructs the same canonical request bytes and nonce, and returns the canonical showing plus a terminal signature over the base request, complete snapshot, full circuit id, and showing bytes. Benchmark-only in-memory issuer state is not a deployment key store.

Required negative gates are cross-deployment showing reuse, full-circuit substitution under the same legacy value, verifier-parameter substitution, same tuple version with a different snapshot, terminal/resource/action recombination, every canonical request field mutation, retired snapshot at Delta zero, expiry crossed while waiting for the commit lock, and concurrent nonce replay.
